0全景：一个生产级 Agent 系统由什么组成

┌─ 模型层        智商从哪来：API/本地模型、参数、结构化输出、选型
├─ 上下文与提示层  喂给模型什么：提示工程、上下文工程、Prompt 版本管理
├─ 工具层         手脚：Function Calling / MCP / Skill、工具设计规范
├─ 知识层(RAG)    外挂知识：切块→检索→重排→生成→引用/拒答
├─ 记忆层         连续性：短期上下文、长期存储、偏好沉淀
├─ 编排层         骨架：工作流 vs Agent、循环、框架、状态持久化、终止与预算
├─ 安全与权限     护栏：注入、最小权限、人工介入、沙箱
├─ 评测          及格线：三层评测、评测集、回归门禁（岗位需求第一名）
├─ 可观测与成本   仪表盘：Trace、P95、每任务成本
└─ 集成交付       最后一公里：IM/OA/审批流对接、灰度、人工基线对比

一条主线记住它：模型是智商，上下文是喂给智商的输入，工具是手脚，RAG 是外挂知识库，记忆是连续性，编排是骨架；评测、可观测、安全这三层不决定 demo 能不能跑，决定系统能不能上生产。演示级与生产级的差距，99% 不在模型，在这些工程层。

1模型层：调用、参数与选型

1.1 调用参数里真正要懂的三件事

  • Temperature（随机性）：0 = 每次输出趋同，0.7 上下 = 更发散。可靠性优先的任务（抽取、分类、工具调用）用 0 或低温；创作类才升温。
  • 上下文窗口：模型一次能"看见"的上限。超限不是报错就是静默截断，长文档必须靠 RAG 或压缩解决，不能硬塞。
  • 输出不确定性：语言模型本质是概率生成。凡是要"稳定"的系统，都要在模型外面套确定性约束（见 1.2）。

1.2 结构化输出：约束生成 + 验证 + 重试

生产系统让模型输出 JSON 的标准三段式：约束生成（给明确 Schema）→ 验证（Pydantic + Instructor）→ 重试（把报错喂回去修一次，再失败才优雅报错）。这个模式个人项目里极少见，恰恰是生产系统的日常。

1.3 模型选型：用数据，不用口碑

  • 同条件对比：同一硬件、同一套 30–50 条标准化测试 Prompt，比内存、吞吐、首 Token 延迟、输出质量，写成对比报告。
  • 量化取舍：本地部署测 GGUF Q4/Q5 档位，记录"质量掉多少、速度涨多少"。
  • 决策维度：API vs 本地，按隐私、延迟、成本、离线四因素判。
  • 微调的定位：不是"让模型更聪明"，而是"在一个定义清楚、Prompt 调不好的任务上持续优秀"。先展示 Prompt 基线，再用指标证明提升。适合任务：非结构化文本→结构化 JSON 抽取、工具调用准确率。数据 2k–10k 条，质量远比数量重要。
  • 按"每完成任务"计成本，而不是按每次调用——更便宜的模型若轮数更多、失败更多，并不更便宜；结果接近且成本可容时选更强的，质量驱动采用与留存。Prompt 是调在具体模型上的，跨模型扫描前先在新候选的失败样例上迭代几轮再淘汰。

1.4 概念层词典（能对话即可）

2上下文与提示层

2.1 提示工程：原则与常用策略

  • 给角色和目标（"你是差旅政策助手…"）；
  • Few-shot 示例：给 2–3 个输入输出样例，比长篇描述管用；
  • 明确输出格式（配合 Schema）；复杂任务让模型"先想后答"；
  • 把注意事项写成负面清单（"不要编造，检索不到就说检索不到"）。

2.2 上下文工程：Agent 失败的第一原因

Agent 出错多数不是模型笨，而是没拿到正确的信息，或信息格式太糟。上下文工程四种手段：

手段做法
写入往上下文里放什么：系统提示、工具结果、检索片段、历史摘要
选择该放哪些：检索 TopK 精选、按相关性过滤，而不是全量倾倒
压缩历史对话摘要化、工具结果提炼后再入上下文
隔离子任务拆到独立上下文，互不污染

合格标准：能说清每一步进模型上下文的具体内容是什么、为什么。框架常常把这件事藏起来，要主动揭开看。

2.3 Prompt 版本管理

Prompt 是系统架构的一部分，改 Prompt 对行为的影响不亚于改代码。规范：所有 Prompt 存进带版本的配置文件/仓库，改动走代码同级流程（评审、可回滚、变更记录）。

3工具层：Function Calling、MCP、Skill

3.1 三者定位（必考概念题）

是什么解决什么
Function Calling模型调用外部工具的底层机制：参数 Schema → 模型决定调用 → 宿主执行 → 结果回填 → 继续让模型能"动手"
MCP工具/数据源接入的标准化协议一次封装，任何支持 MCP 的宿主都能用；对接内部系统的事实标准方向
Skill把领域知识/操作流程打包成按需加载的指令包让模型按场景加载"作业指导书"，而不是全部常驻上下文

层次关系一句话：FC 是机制，MCP 是协议，Skill 是知识封装。把自家工具封装成 MCP Server 是当前公认的加分实践。

3.2 工具设计规范（Agent 能力上限的决定因素）

Agent 的能力上限取决于工具的质量，而不是模型的智商。四条硬规范：

  1. 清晰命名：工具名自解释，get_flight_list 优于 tool1；
  2. 参数 Schema 明确：类型、必填/可选、取值范围；
  3. 错误信息"简短且有指导性"：返回给模型的错误要能引导它纠正（"日期格式应为 YYYY-MM-DD，请修正后重试"）——模型读不懂的错误等于没有错误；
  4. 工具分级：只读查询类与有副作用的写入类，从命名到权限到执行路径都分开管理。

还有两条商业一线验证过的工具原则：工具调用你已有的系统，而不是重新实现它的逻辑——搜索排序、购物车、库存、风控这些系统沉淀了多年调优，工具的边界就是系统逻辑的尽头、模型判断的起点（调用 search_products 时结果应已排好序，模型的活是决定展示哪些、怎么展示）；工具结果就是上下文——只返回模型要推理的字段（搜索行里捎带图片 URL 是惯犯），错误要返回指令而不是错误码（"查询库存请带商品 ID"胜过一个裸 403）。

3.3 Prompt 还是 Skill：按频次决定

装载一个 Skill 要多花一轮模型调用，所以按频次决定放哪：覆盖约三分之一以上流量的指令放系统提示，长尾能力做成 Skill；安全、法务、品牌约束和关键用户事实（过敏原这类）永远放系统提示；能从信号预测的 Skill（比如用户从商品页进入）由 harness 在首轮前直接注入，省掉装载轮。

3.4 UI 组件即工具

业务 Agent 的回复大多是界面组件（商品卡片、行程、对比表），而不是散文——让模型输出结构化 Schema，而不是自造标签再让客户端解析。自造标签路线会随组件增长失控：模型对私有标记不如对工具调用可靠、标签定义膨胀系统提示、历史会话只有自研解析器能读。成熟模式是每个组件就是一个工具（present_products / present_plan_comparison 这类），模型带类型化参数调用，服务端校验并渲染；组件天然留在消息数组里，重新加载历史无需二次解析。组件参数要按渲染结构组织（有序的行与轮播，而不是会被客户端重排的平铺列表），这样用户说"第一个酒店"时，Agent 能从上一次展示调用的参数里知道屏幕上有什么。代价是流式粒度：工具参数按块缓冲校验，组件分步到达；要逐 Token 流式需开启 eager 流式并包一层重试。

4知识层：RAG 全链路

4.1 为什么用 RAG

知识需要新鲜、私有、可引用时用 RAG：不用重训模型、答案能给出处、知识更新就是更新文档。

4.2 主流程七步（每步的"为什么"）

步骤做什么关键点
1 解析清洗PDF/网页/Markdown → 纯文本网页内容先去噪（导航/广告），噪声不除检索必脏
2 切块每块 500–800 Token，相邻 ~100 Token 重叠重叠防切断语义；噪声大的网页用朴素滑动窗优于递归切分
3 向量化Embedding 后存向量库（Chroma/Weaviate 起步）向量库解决"语义相似度检索"，不是普通存储
4 检索TopK 取回相关块混合检索：BM25 关键词 + 向量语义再融合——具体术语靠关键词，模糊意图靠语义
5 重排Cross-Encoder 对（问题，块）成对重打分粗排召回全、精排排得准
6 生成问题+召回块+引用要求交给模型强制答案标注出处
7 拒答约束证据不足时必须拒答只有建立在证据上、敢说"资料里没有"的系统才值得信任

查询侧还有两招：查询改写（口语问题改写成检索友好形式）与元数据过滤（按部门/日期/文档类型先过滤再检索）。

案例（网页 RAG 项目）：作者的练手项目是"从网页搜索某车手/演员的信息并匹配准确度"。经验：多个关键词（人名+作品+身份）应合并组合搜索而不是拆开（拆开放大噪声）；网页噪声大，先去噪提纯文本再用滑动窗切块；用 BM25 粗筛 + LLM 或 Cross-Encoder 精筛解决"召回内容不相关"；网页场景可以不做本地持久化，动态筛选→切块→召回→销毁也是合理架构。下方为该项目反复使用的检索对象示例图。

4.3 进阶方向（概念定位即可）

Graph RAG：知识组织成图谱再检索，适合关系推理密集的领域；Agentic RAG：让 Agent 决定要不要检索、检索什么、检索几轮。普通场景先掌握概念，偏 RAG 岗位才需要深入。

4.4 知识形态的第三阶：把制度做成机器可执行（标准本体）

RAG 之后的第三种知识形态：不再只是检索文本，而是把规则本身建模成结构化、机器可校验执行的知识。国家标准 GB/T 48000《标准数字化》（2025/2026 年发布）给出了完整方法体系：

  • 能力阶梯：L1 电子化（有 PDF）→ L2 结构化（XML/JSON 标记）→ L3 语义化（语义单元与知识图谱，可推理）→ L4 智能化（机器可问答、可校验、可执行）→ L5+ 可拓展；
  • 本体建模：15 类核心实体（标准实体、层次、条款、对象、特性、约束逻辑、行动等）+ 34 个对象属性——把"初始容量应为额定容量的 100%–110%"这类条文，变成机器可直接校验的约束逻辑；
  • 协同制定：9 阶段、8 角色、6 权限的在线协同编写规则（参考 ISO/IEC OSD 平台）。

与第 8 章的关系：RAG 解决"答案从哪来"，本体解决"规则能不能自动判"——合规校验类需求（报销是否超标、流程是否越级）走到 L4 后，判断成本趋近于零。完整知识库见 gbt48000-kb/（00–05）。

4.5 RAG 效果评估（对接第 8 章）

黄金问答集（50–200 条人工确认）+ 指标：忠实度（答案是否被检索片段支持）、引用覆盖率、上下文精度。可用 Ragas 起步。

5记忆层

  • 短期记忆 = 上下文窗口内的对话历史。管理：摘要压缩、关键信息结构化留存。
  • 长期记忆 = 窗口外的持久存储 + 按需检索：偏好、历史决定、实体信息存文件/向量库，用时检索回上下文（本质是"对自己的历史做 RAG"）。
  • 设计要点：记忆要有写入标准（不是什么都记）、过期与冲突策略（新覆盖旧）、膨胀控制（定期摘要归档）。

5.2 工程实现：异步抽取与三层读取

存储用你已有数据库里的小型类型化事实（键、短值、类别、来源会话），按"人"而不止按"账号"建（共享账号场景每人一份，读取遵守该操作员的权限）；写入走异步抽取——每轮或每几轮由独立线程读对话文本并增删改事实，不给用户回合加延迟（内部评测事实召回 +13%）；不要做成"Agent 调用保存工具"：每次保存占一轮还和主任务抢注意力，实测会漏记。抽取器只读用户与助手的文本、不读工具结果——商品描述不能变成关于用户的记忆。读取分三层：常驻上下文（几乎每个请求都依赖的少数事实）、按轮预取（由入口信号预测，搜鞋就带上尺码偏好）、其余走查询工具。隐私四则：写入路径用校验器控制"愿意存哪类记忆"；给用户查看/更正/删除通道并接入注销流程；设保留期防陈旧；按部署地区可整体关闭。

6编排层：从循环到框架到状态

6.1 工作流 vs Agent：第一道架构判断题

工作流是人写死的确定性步骤，可预测、可测试、便宜；Agent 是模型在循环里自主决定下一步，灵活但引入不确定性、成本与失控风险。判断规则（行业共识）：能用确定性工作流稳定解决的，不要用 Agent；大多数业务场景是工作流 + 个别 Agent 节点。能讲清"这里为什么用/不用 Agent"，本身就是工程判断力的证明。

6.2 ReAct 循环骨架

所有 Agent 的内核都是一个循环：思考 → 行动（调工具）→ 观察 → … → 终止。一切框架都是对这个循环的工程化包装。

6.3 框架：会用，更要能拆开看

LangChain 三件套是默认选择，LangGraph 的状态图编排适合带状态的多步任务；其它可选：OpenAI Agents SDK、Pydantic AI、smolagents；低代码平台知道概念即可。框架的共同陷阱：把"每一步到底给模型传了什么"藏起来——选型标准不是流行度，而是你能不能在任意时刻回答"现在上下文里有什么"。

6.4 多 Agent：默认不选

多 Agent 不是高级，是复杂度倍增器（通信、状态同步、责任界定）。实践标准：先做单 Agent，实测瓶颈确实在"单上下文装不下/职责互斥"时才拆。加分写法是对比结论："实测多智能体在本任务上成本高 3 倍而收益不显著，故选单 Agent"。

子代理的两种正当形态：一是当工具用的窄任务委托（如深度调研——搜索、读文档、跑代码、撞南墙都发生在子代理自己的上下文里，只回紧凑结论）；二是该领域已有独立建制的 Agent 时做移交（hand-off）而不是委托——移交把对话归属权交给域 Agent 由它直接面对用户，委托则是主 Agent 每轮把域代理进出拉扯、逐轮劣化。判据是对话归属权。

6.5 状态持久化与断点恢复

长任务一定会遇到超时、限流、进程重启，设计前提就是"会坏"：任务状态落盘，崩溃后从断点继续而不是从头重跑（"崩溃后从第 7 步继续"是最有说服力的演示）。注意：框架的 checkpoint 存的是数据不是执行，进程死了任务照样死；真正的持久化执行（Temporal/Restate/Inngest 一类）把执行状态本身托管。配套：重放模式——把录制的输入重新灌进管线复现问题。

6.6 终止条件与预算：一票 hard 规则

每个 Agent 上线前必须有：最大步数、最大 Token 预算、单任务成本上限、超时熔断。一个会无限循环烧钱的 Agent 在生产环境里是事故，不是特性。这条没有例外。

7安全、权限与人工介入

7.1 威胁模型：读到的内容即攻击面

  • 提示词注入：Agent 读的网页、工单、邮件里可以藏指令。防不住注入本身，只能防注入造成损失。
  • 致命三重奏：当系统同时具备 ①接触私有数据 ②接触不可信内容 ③能对外通信，就存在数据被结构性窃取的风险，没有检测手段能 100% 防住。唯一可靠解法：架构上砍掉一条腿。
  • 过度授权（OWASP LLM Top 10 单列项）：最小权限、最小工具集、危险操作强制人工确认。
  • 第三方内容一律消毒：评价、工单、商品名、网页摘要是别人写的——所有第三方 authored 的工具结果过同一道 sanitizer（剥离控制字符与双向字符、拆解伪装成对话轮或工具调用的文本、限制长度）并用固定标签围栏包裹；提示词侧立约：围栏内容只许报告、不许执行。

7.2 人工介入（Human-in-the-loop）的正确姿势

  • 什么必须拦：一切有副作用的操作——写数据库、发消息、下单支付、提交代码、花钱。
  • 正确实现：任务挂起等批准信号后恢复，而不是进程空转轮询烧资源。
  • 防审批疲劳：只拦真危险的，且把"即将执行什么、影响多大"讲清楚再请求批准。
  • 边界设计模板（订票助手）：查航班/查政策 = 只读直接执行；下单 = 生成草稿 → 人工确认 → 执行；超预算 = 升级人工，Agent 不做主。

7.3 沙箱与审计

模型生成的代码一律沙箱执行（E2B 类服务或 Docker 隔离），永远不在宿主机直接 exec；浏览器操作放隔离环境；每一步工具调用留痕（谁、何时、调了什么、参数结果），出事时要能回答"它到底做了什么"。

7.4 模型提议、harness 执行：staging–apply 与 ID 白名单

提示词是安全行为的起点，但不能是执行点——一次注入或一个坏样本就能让它被跳过。四条代码级执行：(1) 模型只提议（staging），人或策略来执行（apply）：下单、支付、退款、改价、上活动都不落在模型工具上——消费侧用结构解决（结账工具只渲染购物车和按钮，后端接口根本没有扣款方法）；企业侧每个写工具产出带服务端 ID 的暂存变更，apply 只对经真实界面批准的 ID 生效，且 apply 时按当前限额重新校验，而不是沿用暂存时的限额。(2) 写与渲染只收服务器签发的 ID：harness 记录本会话服务端发过的全部 ID，幻觉出来的、用户粘贴的、藏在评论里植入的 ID 一律在后端之前拒收；子代理只读数据、不扩张可写集合。(3) 限额按结果状态执行并串行化会话写：Agent 会重试、改写、并行调用——"再加两件"不能叠加突破上限，封顶类规则校验写入后的状态。(4) 受管文案（费率、披露）由模型选择展示哪条、服务端逐字供给已审定稿，评测逐字节比对渲染串。

8评测：Agent 部门的第一基础设施

8.1 为什么排第一

对招聘岗位 JD 的关键词统计：55.7% 的 AI 工程岗位明确要求评测能力，提到 Agent 的岗位里 68.4% 同时要求评测——两项都是第一名。企业要的不是"做过 Agent 的人"，是"能证明这个 Agent 到底好不好的人"。

8.2 评什么：轨迹，不只是结果

层问的问题用途
最终结果评测任务到底成没成功汇报成功率
轨迹评测路径合理吗？工具调用序列对吗？要能给部分分：前几步对只错最后一步 ≠ 一开始就跑偏
单步评测单看这一步选得对不对定位调试

轨迹比对注意：不同顺序调用了同一批工具通常应算对，严格顺序匹配会误判（agentevals 库支持无序/子集匹配）。

裁决：门禁评快照，调试评轨迹。行业另一主流主张"评快照不评路径"：模型 API 无状态，任何对话状态都可以直接构造——造出测试态、追加测试消息、跑 Agent，然后只评最终状态与渲染结果（含最后一次写操作的参数），对路径的断言脆弱且限制实现。这与三层评测不矛盾，按用途分工：上线门禁用快照结果（稳定、可构造、不脆弱）；轨迹与单步评测降级为调试定位手段，不作发布门槛。模拟用户评测（第二个模型扮用户、裁判评全程）只用于发现覆盖缺口，不用于测量。

8.3 怎么评：可复现、多次跑、算成本

  • 前提：任务设计成"成败能自动判定"，不能自动判定的选题直接淘汰；
  • 环境固定：外部依赖固定/mock，同一任务能反复重跑；
  • 多次重复，报区间：同配置跑 N 次报波动区间——有审计显示相同配置重复 23 次，成绩从 57.9% 到 76.8% 不等，单次运行的数字基本等于噪声；
  • 失败归因：失败样本自动归类（工具用错 / 上下文丢失 / 陷入循环 / 过早宣布完成）；
  • LLM 当裁判不可靠：没有一个 LLM 裁判精确率超过 70%。裁判能不用就不用，要用必须抽样人工复核校准。
  • 脏条件与负面用例：多数套例挂在干净状态上，要专门造长而乱、自相矛盾的前置历史；每个正面用例配负面对（应服务/应拒答、应直接做/应先问）——缺负面是最常见的套例缺口；注入拆两例：用户消息注入 vs 数据面注入（藏在商品名/评论/网页摘要里随工具结果进来）；跨能力组合请求单独写例（"降价 15% 库存够吗"=定价+库存两问，逐能力写的评测各自只核自己那半）；受管文案逐字节比对。用例与业务专家（客服/法务/运营）共写，真实事故是最好的用例，每个用户流 50–100 条起步。

8.4 回归门禁：评测进 CI

评测集接入持续集成：每次改动自动跑评测，低于阈值就阻断发布。这是"生产团队天天用、个人项目几乎没人做"的纪律。

组织级协作要点：所有权跟着系统走（每个 Skill/工具有唯一归属团队，共享提示词分平台段与域段双属主）；变更自带用例，CI 按影响分层跑——核心高流量集与全部安全例必跑，改 Skill 跑自身+邻域边界例，改共享提示词跑全量；门禁看多次试用的通过率，外加缓存命中率与每轮成本；夜间全量+发布前全量抓跨团队回归；Agent 进发布日历：金丝雀灰度、单 Skill 热开关、高峰期前冻结。

8.5 公开基准与脚手架消融

成本可控的基准：τ²-bench（客服工具调用）、BFCL 函数调用榜；SWE-bench 只跑子集。关键事实：同一个模型仅因脚手架不同，成绩能差 19.6 个百分点——模型不是变量，工程才是。专业报告会做消融，把"脚手架的贡献"和"模型的贡献"分开呈现。

9可观测性与成本

9.1 全链路 Trace

生产环境里"构建系统"只占 30% 的工作，70% 是搞清它运行得对不对。每个请求应能追溯：检索回了什么 → 重排怎么改序 → 发给模型的完整 Prompt → 返回什么 → 用了多少 Token。工具：Langfuse（开源可自托管，推荐起步）、LangSmith（LangChain 原生）。

9.2 指标清单

指标为什么
P50 / P95 延迟平均值掩盖最差体验，P95 才是用户真实痛感
每请求/每任务成本用金额说话，ROI 的分子分母全靠它
引用覆盖率多少回答真建立在证据上（防编造的量化）
失败率 / 拒答率系统多频繁报错或拒答
人工介入率过高=自动化失败，过低=可能失控
超预算终止率预算设置是否合理

合格标准：别人问"上周二质量下降发生了什么"，你能打开仪表盘指出异常并解释根因。

9.3 成本工程的残酷与现实

相同准确率的两个配置，成本可以差 64 倍；某基准上 56.0% 准确率的配置花 $11，54.0% 的花 $180——省掉 2 个百分点的指标，多花 16 倍的钱。优化顺序：先砍提示词/上下文冗余（Token 大头），再调模型档位，最后才考虑架构重构。

缓存按变更频率分三段排序：全局段（系统提示+工具定义，跨会话字节级一致、最暖）→ 会话段（用户上下文与历史）→ 易变段（当前时间、当前页面——放请求最末；最常见的翻车是把时间戳写在系统提示开头，每个请求都静默打穿缓存）。断点逐轮前滚：新断点移到最新用户轮末尾，让长工具结果（如检索响应）随历史一起走缓存；Skill 以工具结果形式装载（落进会话前缀被缓存），不要追加进系统提示。头部部署的命中率在 90–99%——把它当设计目标；命中读取在 10 万 Token 量级还快 1.5–2 倍。

10从演示到生产：交付纪律

三阶段通法：

  1. 基础功能：端到端跑通，能演示"输入→答案→依据"；
  2. 生产质量：混合检索/重排（RAG）或工具规范/权限分级（Agent）、引用与拒答约束、Prompt 版本化、错误处理与超时；
  3. 交付能力：黄金评测集、CI 回归门禁、全链路 Trace、成本上报、人工基线对比——AI 方案必须和"这件事人工怎么做、单件几分钟、错多少"同口径比，ROI 才算得出来。
  • 延迟预算拆解：端到端延迟拆到组件（"总响应 1.2s，其中检索 0.3s、首 Token 0.6s…"），能这么汇报的人天然可信；
  • 任务完成延迟的三杠杆：总延迟 = 各轮 Token 时间 + 工具耗时之和；杠杆是更少轮数（预载可能用到的上下文、更强模型规划、独立工具并行调用）、更快工具（后端优化＋参数流完即执行，最慢的调用先发）、更快 Token（按评测扫描选型）——杠杆互斥，优化总和而非单项；
  • 感知延迟单独优化：让屏幕早点动——组件流式渐进渲染（一次业务回复约 500–700 输出 Token，不流式就是五秒以上的转圈），干活时用大白话逐步播报（"正在找海边的酒店"）；指标上结果质量对留存/转化的影响大于边际延迟，目标是待在用户的延迟预算内。
  • 韧性三件：超时处理、优雅降级、重放调试；
  • 汇报表达铁律：写"测出了什么"，不写"用了什么"。"使用 LangChain+ChromaDB 构建 RAG" ❌ → "自建 200 条黄金评测集接入 CI，忠实度低于 0.85 阻断合并" ✅。每条 = 动作 + 机制 + 数字；
  • 量力而行：写了超出自己驾驭水平的东西，一问就穿帮，反而减分。在能力范围内做最深的，然后诚实呈现。

11反模式清单（出现任何一条，评审直接打回）

#反模式正确姿势
1演示一次跑通就算成功多次重复报成功率区间（单次=噪声）
2无终止条件/无预算上限最大步数 + Token/金额上限 + 超时熔断
