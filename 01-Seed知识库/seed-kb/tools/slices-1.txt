4.8.2 大模型的计费标准​
4.8.2.1 先看懂：你跟 AI 说一句话，背后发生了什么​
在谈钱之前，先弄清一次对话的完整过程——不然后面那些输入、缓存、输出你会对不上号。​
你每发一条消息，模型并不是只读你那句话。它每一轮都要把整个上下文从头到尾读一遍，然后才生成回复。这个上下文包括（这里是粗略地讲，其实Agent的上下文内容，我们每个Agent架构都会专门讲解，但本节主要是聚焦于计费，不深究上下文细节，以下是最典型的模型上下文组成）：​
系统提示 + 工具定义（Claude Code 内置的一大段说明，最靠前）​
项目信息（你的 CLAUDE.md、memory 等）​
之前的完整对话历史（前面每一轮的问和答）​
你这一轮新说的话​
把这 4 块加起来，模型读进去的全部，叫 输入（input）；模型写出来的回复，叫 输出（output）。​
关键问题来了：第 ①②③ 块，其实每一轮都长得一模一样（系统提示不变、CLAUDE.md 不变、已发生的历史也不会变），只有第 ④ 块每轮才新增。如果每轮都把 ①②③ 当成全新内容重新读一遍并收全价，那太浪费了。于是就有了缓存：把这些重复不变的部分存起来，下一轮直接复用。​
这就引出了收费的逻辑。下面这张图把一次请求怎么被拆分收费画清楚。核心逻辑是：​
一次请求 = 输入 + 输出两部分收费。输出只有一种（最贵）。而输入会按有没有命中缓存分成三条路，每条价格不同。​
❓ 你可能会先问：为什么一次大模型请求的费用要分成输入和输出两部分？​
因为大模型推理本身就分成两个截然不同的阶段，成本差异很大。做过模型推理的同学应该清楚，这两个阶段叫 prefill（预填充） 和 decode（解码）——输入正对应 prefill，输出正对应 decode。​
prefill（对应输入）：把你的整段 prompt 一次性读进去理解。这些 token 可以并行处理，GPU 一口气就能吞一大批，算得快、摊到每个 token 的成本低 → 所以输入便宜。​
decode（对应输出）：生成回复时只能一个字一个字往外蹦（每个新词都依赖前一个，没法并行），每生成一个 token 都要把整个模型重跑一遍，慢且吃算力 → 所以输出最贵。​
一句话：因为读 prompt 和写回复是两种成本完全不同的计算，所以要分开计费——这也是为什么后面输出的单价会远高于输入。​
这一次请求会被拆成四种收费名目：​
① 缓存写入 cache write（5m / 1h 两种时长）：发生在某段内容首次出现的那一轮——内容第一次被读，并存进缓存。​
② 缓存读取 cache read（便宜 10 倍）：发生在后续每一轮复用它时——内容没变、还没过期，直接复用。​
③ 基础输入 input（全价）：发生在缓存过期/失效后重读，或某段内容压根没被缓存时——当成全新内容来读。​
④ 输出 output（最贵）：发生在每一轮的回答——模型生成回复。​
一句话串起来：同一段内容第一次见 → 走写入存起来；以后复用 → 走便宜的读取；如果缓存没了、当新的重读 → 走全价输入；模型的回答 → 走最贵的输出。 省 token 的所有招数，本质都是在操控这几个阶段的走向（让更多内容走②便宜读取、少走③④）。​
理解了这个过程，再看下面的价目就顺了。​

输出最贵（约输入的 5 倍）。所以让模型少说废话省下的是最贵的那种 token——这就是让 Claude 简洁回答为什么划算。​
写入缓存略贵一点（1.25×），是一次性成本，下一轮就靠便宜的读取回本。所以频繁打破缓存 = 反复付这笔写入费，特别亏。​
4.8.3 Claude Code 的提示词缓存策略​
上一章讲清了怎么收费，这一章讲清缓存怎么运作——它是 Claude Code 的内置行为，不用装任何东西，但理解它是后面所有最佳实践的根基。​
缓存是什么：复印 + 存档​
把缓存想象成复印存档：​
cache create（缓存创建） ＝ 第一次把内容复印、归档。有成本，但只花一次。​
cache read（缓存读取） ＝ 之后直接从档案柜拿复印件，不用重新处理，便宜约 10 倍。​
同一段内容，第一次见按 create 收费，以后每次复用按 read 收费。省钱的关键就一句话：让尽量多的内容走便宜的 read。 而且这一切自动发生，你不用配置。​
缓存分三层：范围越大越省​
Claude 的缓存按能被多大范围复用分三层，越靠前越稳定、越多会话共享：​
系统层：内容是基础指令、工具定义，复用范围是全局（所有会话共享）。​
项目层：内容是 CLAUDE.md、memory，复用范围是按项目。​
对话层：内容是你的消息、回复，复用范围是仅当前会话。​
TTL：缓存能活多久​
TTL 是缓存闲置多久后过期。每次活跃使用都会重置计时，只有长时间不碰才作废。​
订阅版 / Claude Code：1 小时 ​
API 付费 / 子代理：5 分钟​
缓存是怎么随对话一轮轮增长的​
知道了缓存的分类，还得看清缓存在多轮对话里怎么一步步长大——这决定了你什么时候便宜、什么时候突然变贵。​
核心机制叫 前缀匹配（prefix matching）：缓存是从最开头起、一段段往后叠的。每一轮都会把完整上下文重新发一遍，其中没变的前缀部分直接读缓存（便宜），只有新增的部分才需要写入缓存。​
用图里的四轮来看：​
第 1 轮：全新开始，还没有任何缓存。系统提示 + 项目上下文 + 消息1 全部要处理并写入缓存（这一轮最贵）。​
第 2 轮：前面那一整块（系统提示、项目上下文、消息1）没变 → 直接读缓存；只有新增的回复1 + 消息2需要写入缓存。​
第 3 轮：同理，前面全部读缓存，只有新增的回复2 + 消息3写入。越往后，便宜的读取占比越高——这就是为什么长会话反而越用越省。​
第 4 轮（系统提示被改了）：因为最靠前的系统提示变了，整个前缀的指纹对不上了，从它往后的所有内容——哪怕一个字没改——都得重新处理、重新写入。一夜回到第 1 轮，一次昂贵的重算。​
什么会打破缓存​
缓存是前缀匹配——从头往后一段段叠。只要动了靠前的内容，从那点往后全部作废、要重新 create。 触发情形：​
闲置超过 TTL（缓存过期）​
切换模型​
改系统提示​
执行 /compact​
（注意：改 CLAUDE.md 反而不会立刻失效，重启会话才生效。）​
这就解释了核心结论：只要动了靠前的东西（改系统提示、切模型、或让缓存过期），前缀就断了，后面全部作废重来。 往后追加新对话是安全的，动前面是致命的。​
📎 提示词缓存的完整机制其实相当复杂——它还涉及缓存断点（breakpoint）、20 个块的回看窗口、最小可缓存 token 数（多数模型 1024 起）、不同改动对 tools/system/messages 各层的影响等等。​
日常使用记住别动前缀这一条就够了；想深入了解的，可以看 Anthropic 官方文档：https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching​
4.8.4 最佳实践​
理解了计费和缓存，就能推出该怎么做了。分两类：免费无副作用的习惯（顺应缓存）和主动削减投喂的工具（各有取舍）。下面每一类都给出市面主流、开源免费的成熟替代品（均为公开 GitHub 项目，不依赖任何付费社区）。​
4.8.4.1  先养成三个免费习惯（顺应缓存）​
别停太久——超 1 小时缓存就凉，别把庞大旧历史拖回来重造，因为反正你过去的缓存都已经无效了，干脆我彻底整理一波，让上下文处于最有效的状态。这里有两种做法： 一种是可以使用compact压缩历史，带着更简单的上下文继续。 一种是使用一些skill，比如像Nate（我经常跟着学习的专门做ClaudeCode自动化的博主）提供的handoff skill，使用这个skill重新开一个新会话，并把前一段会话上下文整理打包过来，本质是使用Harness技巧总结好一次会话的精髓，使用新的上下文来延续上一次会话。​
切任务就 /clear——旧任务的长历史对新任务无用，却每轮重复计费。​
切模型别中途切——切模型这件事会破坏缓存，要用的模型就一开始定好，避免打破缓存。​
这套原理对省 token 的意义：你花的每一分钱，要么是复用已缓存的（便宜 read），要么是被迫重造（昂贵 create）。上面三个习惯，本质都是别让缓存无谓地失效。​
4.8.4.2 先诊断：不知道浪费在哪就没法省​
原理：每次开会话，CLAUDE.md、skills、MCP、slash 命令、hooks 都会被加载进上下文，凭空吃掉 token（大头常是 skills 和 MCP）。得先量出来花在哪，才能对症下药。​
ccusage 读本地会话日志，生成每日/每周/每会话的 token 与花费报告。npx ccusage 即用，还同时支持 Codex、Gemini CLI。​
Claude-Code-Usage-Monitor 实时终端面板，带用量预测和告警，适合盯着别超额度。​
/context（内置免费）：不装任何东西，直接看当前上下文构成，最轻量的自查方式，因为通常工具自带的查花费的手段，不是那么清晰，所以才会有专门的这些工具更细致地统计。​
4.8.4.3 削减输入 token​
原理：默认情况下 Claude 靠 grep + 逐块读文件来定位相关代码，这个摸索过程很费 token。给它更好的检索方式或现成的项目地图，就能少读很多无关文件。这个你看了我们笔记中Harness讲解检索的章节就很容易理解，本质上就是修改工具的检索方法。不同的检索方法特点不同，CC使用的是更通用的方法，如果想要更省钱，可以建立索引。​
Serena 开源 MCP 工具包，提供符号级的语义代码检索/编辑/重构能力，支持 40+ 语言。相当于代码索引图谱的主流替代：让 Claude 按符号精准定位，而不是大段读文件。​
mcp-language-server 把语言服务器（LSP）能力接给 AI，支持查定义、找引用、看诊断。更轻量的语义导航方案。​
写好项目文档（免费、最易做）：在 CLAUDE.md 或分目录的说明文件里，把每块代码干嘛、有哪些约定和坑写清楚。为什么省：Claude 不用每次重新摸索项目结构——这就是 Intent Layer 的核心思想，其实手写一份就能实现，不必装工具。​
4.8.4.4 削减输出 token​
原理：模型爱写铺垫、叙述、总结，这些最费输出 token，而多轮对话里会不断累积。让它说话简洁即可。​
不必装工具：网上有个流行的 Caveman skill（「原始人 skill」，slogan 是「why use many token when few token do trick」），思路就是逼 Claude 像原始人一样用最少的字说话、砍掉一切废话，官方称能省下约 65% 的输出 token。但它本质上不神秘——你自己在 CLAUDE.md 里写一句约束就能实现同样效果，例如「回答简洁直接，省略铺垫和客套，保留必要的技术细节」。代价也一样：说太少时复杂任务可能降质，需要详解时临时放开即可。​
4.8.4.5  会话与文档管理​
交接会话：可以使用 Handoff Skill（夸克网盘），让 Claude 总结当前会话中做了什么、下一步做什么，再开启新会话继续。也可以让 Claude 手动总结后执行 /clear，或者使用内置的 /compact。为什么省：不必拖着长上下文每轮重复计费。​
写好 CLAUDE.md（免费）：保持 <300 行，只写模型猜不到的（项目意图、非显而易见的版本/工具约束、偏离常规的架构、踩过的坑）。为什么省：短而精的文档既减少每次加载的 token，又避免模型自作主张走弯路。旧式命名规范那类是浪费。​
切模型：简单/重复任务用更便宜的小模型。为什么省：小模型单价低。但记得——要用就一开始选定，别中途切（否则打破缓存）。​
❗ 这些方法对其他工具（如 Codex）适用吗？​
原理层：思维通用（前缀缓存、动了靠前的就全废、稳定内容放前面），但数字不通用——Codex（OpenAI）的 TTL 更短且不可控，缓存折扣更小（约省 50% 而非 90%），命令也全不同。​
工具层：大多跨工具通用。语义检索（Serena 等）、用量统计（ccusage 直接支持 Codex）、写好项目文档，本质是处理文件/上下文/用量，和用哪个模型无关。​
一句话：原理层照搬思维、本地化数字；工具层大多能直接迁移。​
4.8.4.6 工具速查​
查 token 用量/花费（支持 Codex、Gemini） → ccusage​

5. Vibe Coding​
Vibe Coding 已经是现在绕不开的趋势了。虽然本节归在了其它问题，但是我强调的本节其实也非常重要。​
面试的角度它很重要：可以看到网龙面试环节问Vibe Coding的经验，我也遇到很多面试官会问你最喜欢使用哪个Vibecoding的 工具等，其实这些都是企业对于你的考察，因为在新的时代的来临，程序员的编程方式一定会发生变化，如何高效vibe code, 聪明使用AI工具一定是企业看中的，因此虽然他不是一个硬核知识考点，但绝对也是面试中热门的话题，这个问题答的好，一定是一个加分点。​
个人成长的角度上：它也太重要了。现在谁不vibe coding呢？谁不会聊两句你是如何使用AI工具编程的呢？学会高效使用VibeCoding对个人成长必不可少。​
所以本节内容其实很重要，而且这个内容甚至适合于任何人，你甚至可以是产品经理或者没有任何开发背景的人，因为VibeCoding极大降低了编程门槛。​
本节会推荐5个Vibe Coding的视频，同时根据视频也整理成了文字精髓放在这个小节。看完本节，你会学习到Vibe Coding的推荐方法，行业发展/Vibe Coding的趋势。 相信本节内容也会给你带来灵感。​
5.1 核心技巧​
Vibe Coding的有5大核心基础：思考，架构，节点，调试，上下文。​
5.1.1 思考细致​
在使用AI工具前，你需要仔细思考你到底想要什么。如果你自己都没想明白，你怎么能期望AI能够写明白？在我们vibe coding的时候都使用的自然语言，很容易没有想清楚我们到底想要一个什么样的产品，其实这个阶段是我们很好的仔细思考，提升自我的机会。必须仔细想清楚，想实现的目标是什么，它应该怎么实现，需要哪些条件和能力，他要遵循什么样的规则，它的流程是什么。 将问题想清楚，再以自然语言的形式描述给AI。​
5.1.2 明确架构​
我们使用VibeCoding的时候，几乎一定有现成的架构或者类似的任务的。我们需要让AI遵循指定的架构，或者使用指定库，这样效果一定会比让他从头完成更好。我们需要给AI指明一个方向。比如，对于一个浏览器应用，你可以明确它使用React前端，CSS和HTML JavaScript前端。​
（如果你不知道采用哪种架构，没关系，可以先让AI给你提供一些可能的方向，然后以学习的心态去学习，确定好对应的架构，可以在vibecoding的时候同时进行学习）​
5.1.3 做好版本控制​
系统可能崩溃，所以始终做好版本控制和节点管理。​
5.1.4 调试​
通常在Vibe Coding中，最快修复问题的方式是指出问题，让AI自己修复。但有时可能会遇到一些问题，AI并不能很轻易地解决，这时就需要我们对系统有一个问题更深入的理解，缩小范围，推测可能的原因帮助AI解决问题。​
5.1.5 提供上下文​
你提供更多的细节，信息，上下文，你的AI的输出就会越好。这些信息包括，具体的产品文档，你的环境，你的倾向，示例，或者是更加精心打磨的上下文，这些都能够帮助AI取得更好的效果。​
5.2 建议​
总是先完成一个最小可以运行的产品，然后再迭代，增加更多的feature.​
在你使用AI coding的时候，一般只有两种模式，你要么是在添加新feature，要么是在调试错误。添加新feature时，记住提供更多的信息，明确架构，给出有明确细节的参考文档，增量修改，做好版本管理和控制。当你在调试的时候，记住弄清楚系统是怎么运行的（如果不清楚，就问AI），给出尽可能多的信息，想想如何能让AI解决这个BUG。​
给出全局的约束。这个有点像将要求放在系统提示词中，让AI Coding的时候总是遵循某个规则，比如尽量少的改动代码，以xx的规范来完成。​

在大模型这个行业，和我们传统开发不一样。即使是开发，也是需要读论文的，我从三个点来说明为什么：​
面试需要：这点你从我的面试记录中可以看出来，很多公司是直接会问你最近读过什么论文的。这点在传统开发领域几乎不会出现，而在大模型方向，即使是应用岗，该问题出现的频率也很高。从清华大学出版社《大模型工程师面试 - 算法原理，开发实践与系统部署中》也讲了，如果以3个维度（刷题，论文和项目）来衡量大模型岗位准备的优先级。推荐顺序为：​
校招/初级算法岗：刷题>项目≈论文​
高级算法岗: 论文>项目≈刷题​
Agent/Rag 方向开发： 项目≈论文>刷题​
算法岗就不说了，肯定要看论文的。但是对于开发岗，书上明确将论文和项目放在了同一等级。 至于这个优先级排序，我觉得我们也不用较真，但是可以看出的是，书中明确将论文作为大模型开发方向的一个重要准备方向,和我的个人实践一样，确实是需要准备的。​
确实有用： 大模型这个行业发展很快。即使是Agent，有人称2025年是Agent元年，现在2026年，Agent发展也不过一年。行业中以什么样的形式组织Agent，什么样的Agent框架最好，怎么评估Agent这些工程方面的东西，都还在研究和讨论。书和资料更多的是一些基础知识，但是论文上的知识，有的更加先进，代表未来的方向，会给我们不一样的启示。看了很多论文，对我们工程也确实有帮助，比如有的论文写如何选Agent架构，项目的Agents.md如何组织最好这些东西对我们工程最佳实践也有帮助。​

Agents​
Evaluating AGENTS.md -Are Repository-Level Context Files Helpful for Coding Agents?​
概述​
越来越多的开发者/公司为代码仓库写一个 AGENTS.md（或 CLAUDE.md）文件，相当于一份"仓库说明书"，告诉 AI 编程智能体：项目结构概览，用哪些工具（如 uv、ruff)，遵守哪些代码风格，如何运行测试等。OpenAI、Anthropic 等厂商强烈推荐这个做法。截至论文写作时（202602），GitHub 上已有超过 6 万个开源仓库包含此类文件。本篇论文就是在研究，这些东西到底对Agents有没有用？是写的越详细越好吗？有没有可能反而会带来负面影响？​
实验方法​
论文构建了一个新基准 AGENTBENCH（共 138 个真实 GitHub Issue 任务），选自 12 个小众但有开发者提交的 context file 的 Python 仓库，补充已有的 SWE-bench Lite（300 个任务，这个是目前评测 AI 编程智能体能力的一套测试集）。​
对 3个主流 Agent（Claude Code / Codex / Qwen Code）测试了三种设置：​
1.None:不提供任何Context File(AGENTS.md CLAUDE.md)。​
2.LLM：按照厂商推荐的指令，提供使用AI自动生成的Context File。​
3.Human:提供开发者手写的Context File。​
测试方法是对每个PR，给出一个测试用例：<问题描述，PR前的代码仓库，测试集，正确答案>（这个测试集和方式也是 SWE-bench Lite的测试集形式，所以通过这个问题你可以学习了解典型的一种测试AI Coding能力的数据集），让AI完成这个PR。比较AI完成后的问题的：任务完成率，成本（总Token消耗），行为分析（工具调用次数，是否遵循了Context File，有没有运行更多的上下文搜索，做更多的测试等）​
核心发现​
LLM 自动生成的 context file 反而有害。与"不提供任何文件"相比，LLM 生成版本平均使任务成功率下降约 3%，而且推理成本（token 消耗）增加超过 20%，换用更强的模型（如 GPT-5.2）来生成也没有一致改善。​
人类手写的 context file 帮助极为有限。仅带来平均约 +4% 的成功率提升，远低于人们预期。​
iii.
Agent 确实读取并执行了 context file 中的指令。比如 context file 提到使用 uv，Agent 就会用 uv，说明效果差不是因为 Agent 忽略了说明书，而是说明书本身加重了任务难度​
iv.
Context file 导致 Agent 行为更"臃肿"。Agent 运行更多测试、查看更多文件、写更多文件。GPT-5.2 的推理 token 增加了 22%，说明 Agent 认为任务"变难了"​
核心假设：context file 中包含了大量"非必要要求"，这些额外约束反而让 Agent 在完成核心任务时分心、出错，相当于给 Agent "加了很多不必要的作业"。​
核心结论​
对面试的帮助​
Agent评估：看完了本论文，其实你又可以进一步理解Agents评估。比如本文对Coding Agents的评估维度是：正确率，轨迹路径（调用工具次数，是否遵循了指令，是否阅读了更上下文，做了更多次数），成本(总Token消耗，推理Token消耗）​
